# Decisions in force — Calendar

> Current guidance, kept up to date; not a decision record. The ADRs linked here decide: where this page and an Accepted ADR disagree, the ADR holds.

_Last reviewed: 2026-11-22_

## Rules in force

- One predicate in `apps/api/src/services/calendarAudience.service.ts` decides both which events a user sees (`eventVisibilityWhere`) and who is notified about them (`resolveEventAudience`): an active, approved user with access to the event's brand for whom the event is relevant. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- A function counts only on the brands of the same active team: `getUserAllowedIds` returns the function → brands pairs (`FunctionBrands`), a team with no brand scope grants its function on nothing, and the rule holds for every read and write that composes `eventVisibilityWhere` (the calendar list, access by id, masking, the save confirmation, the exports) and for the function candidates of `resolveEventAudience`. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- The whole-brand fallback applies only to an event with no visibility rows of either kind, on read and on notify alike, so an event shared only with single people reaches only them. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- `grantUserVisibility` refuses with `PRECONDITION_FAILED` a per-person row on an event with no visibility row at all, and the share picker offers nobody for it; an event already shared only with people takes more. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- The last per-person row of an event with no function row is never removed: `revokeUserVisibility` refuses it under a row lock, and `users.hardDelete` refuses to delete a user who is the only person of such an event. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- `cloneFromBrandSeason` refuses a source event with per-person rows and no function row, naming only the events the caller can list, while `applyTemplate` still creates events with no row at all, which reach the whole brand. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- An admin reads every brand but is notified only like anyone else, through a team holding the function and brand pair, a team holding the brand for the fallback, or a per-person row; the manual "send to me" digest an admin requests is not an automatic fan-out and stays as it is. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- Of ADR-014 only sub-decisions 3 and 4 stand, kept unchanged by ADR-041: the per-person grant (`CalendarEventUserVisibility`) is the only way to share an event outside its visible functions, with brand access validated at grant time by `grantUserVisibility`. [ADR-014](../014-calendar-visibility-single-predicate.md), [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- No default team is assigned at provisioning (ADR-014 sub-decision 4): a new LDAP user has no team, and `users.approvePending` requires an explicit `teamId`, assigned in the transaction that clears `pendingApproval` ([ADR-044](../044-pending-user-approval-in-one-transaction.md)). [ADR-014](../014-calendar-visibility-single-predicate.md), [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- A deleted event's digest goes to the audience stored at deletion (`visibleUserIds`, resolved by `deleteMilestone` with this predicate), and delivery re-checks brand access; a snapshot taken before ADR-041 is delivered as stored. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- The calendar export routes require `season_calendar:read` and `season_calendar:export`, checked in `resolveParams` right after authentication: 401 without a session, 403 for either missing permission. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- The Google Calendar subscribe panel shows an admin every function's calendar and anyone else a calendar only when a team of theirs holds its function and the calendar's brand. [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- `resolveEventBrandAccess` checks the brand, then `assertEventsVisible`: an event the caller cannot list inside an allowed brand answers `NOT_FOUND` `Evento non trovato`, like a missing id and before anything about its state, a brand outside the caller's scope stays `FORBIDDEN`, and `locate` answers `NOT_FOUND` for both. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- Visibility applies to writes by id as to reads, personal notes and shares included, so `season_calendar:update` does not by itself allow a write; `callerEventVisibility` is joined with `AND: [fragment]` so it cannot overwrite a key of its `where`. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- `deleteMilestones` is all or nothing: a hidden event among the ids answers `NOT_FOUND` and deletes nothing, while an id that does not exist is ignored. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- The visibility check precedes the write without a lock, as the brand check does, a deliberate exception to the check-then-act rule. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- The alert engine stays viewer-independent, and every output that names or dates an event passes through `services/eventMasking.service.ts`, which resolves visibility once per answer and not at all for an admin. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- In a criticality answer a hidden event loses its identity, dates, day counts and counting mode, each for its own event (active, next or completion), the row keeps `state` and `band`, and a concluded row says `eventHidden`. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- In a bottleneck answer hidden events merge into one last entry with summed band counts. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- An automatic revision's note and event reference are removed, in the revision pages and both exports, when the caller cannot list the event, and for a deleted event shown only to an admin; a manual revision's note is its author's, and stored data is not changed. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- Template application and clone still create every event with its visibility, but their answers and refusals name only events the caller can list. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- The holiday warning before a freeze holds the entries the caller can read plus `hiddenCount`, given to every holder of `season_calendar:read`, while the freeze itself snapshots every event of the group. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- These stay visible by design: a row's `state`, `band`, `reached`, `late` and `completedDay`, a hidden event's `phaseId` and `nextPhase.reached`, phase labels in `completionPreview` and the `rows.setCompleted` conflict, `seasonPhaseOrder`, a masked revision's `createdAt`, `cause` and `revisionTypeValue`, the `listTemplates` catalog for holders of `milestone_template:read`, and counts or refusals that name no hidden event. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
- The deadline scheduler and notifications read every event and send only to the audience `resolveEventAudience` resolves under ADR-041's predicate, and `rows.setCompleted` reads every event but answers with phase labels only. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md#errata), [ADR-041](../041-calendar-visibility-function-and-brand-from-one-team.md)
- A new field in `criticalityForRow`'s masked answers fails `apps/api/test/eventMasking.integration.spec.ts`, which asserts them whole, until someone decides it; the other masked answers are asserted by field. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md)
