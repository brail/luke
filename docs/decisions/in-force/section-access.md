# Decisions in force — Section access

> Current guidance, kept up to date; not a decision record. The ADRs linked here decide: where this page and an Accepted ADR disagree, the ADR holds.

_Last reviewed: 2026-11-22_

## Rules in force

- `packages/core/src/rbac/sectionHierarchy.ts` derives the section tree from the dot notation of `sectionEnum`, so a section added as `x.y` joins `x` with no other edit. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- A section with children is on if and only if at least one of its children is, and its own override, role default and permission are never consulted. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- A leaf resolves in `effectiveSectionAccess` (`packages/core/src/rbac/effectiveAccess.ts`) by the kill switch `app.sections.disabled` (denying when the leaf or any section above it is listed, through `isGloballyDisabled`, the one predicate the access dialogs share), then the per-user override, then the role default, then the permission fallback (`SECTION_TO_PERMISSION`, `hasPermission`), which only an explicit `'auto'` or a role outside `Roles` reaches and which denies the latter. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `sectionAccessDefaultsSchema` (`packages/core/src/schemas/rbac.ts`) describes a valid stored `rbac.sectionAccessDefaults` — a partial record over `Roles` of partial records over `sectionEnum`, each `'enabled'`, `'disabled'` or `'auto'` — and both the registry entry and `setRoleDefaults` use it. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `getRbacConfig` reads the stored role map entry by entry: unknown roles and sections are dropped, an invalid value, a role whose value is not an object and a row that is not a JSON object are ignored, and ignored entries are reported by key only, never value, to the handler registered with `setRbacConfigWarningHandler`. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `mergeSectionAccessDefaults` gives each role the static `SECTION_ACCESS_DEFAULTS` with the valid stored entries over it, so an omitted or ignored entry takes its static value, never `'auto'` — the failure mode is availability, not fail-closed — and an unreadable kill-switch row reads as an empty list. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `getRbacConfig` caches for 60 seconds, and `invalidateRbacCache()` must follow every write to an `rbac.*` key or to `app.sections.disabled`. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- Per-user overrides are written through `applySectionOverride` (`apps/api/src/services/sectionAccess.service.ts`), the path of both `sectionAccess.set` and `users.approvePending`, which refuses a section with children for every value, `null` included, and `setOverride` is the one function that writes `user_section_access`. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md#errata)
- `setRoleDefaults` takes `sectionAccessDefaultsSchema`, replaces the stored map while what it omits keeps the static default, counts its last-admin guard against `mergeSectionAccessDefaults(input)`, and is the only write path for the key, since `config.set` refuses the `rbac` prefix. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `saveSectionsDisabled` (`apps/api/src/lib/configManager.ts`) is the only function that saves `app.sections.disabled`, refusing a list that leaves no administrator able to reach user administration and recording the list in its transaction, while `saveConfig` and `saveConfigs` refuse the key and `deleteConfig` removes it, back to its default, with its own row. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md#errata)
- A new section changes `sectionEnum`, `SECTION_TO_PERMISSION` and `SECTION_ACCESS_DEFAULTS` together. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `withSectionAccess(section)` accepts only a section without children, throwing when the procedure is built at module load, reads only the guarded section's override and fails the request on a failed read, and `storage.getConfig` and `storage.saveConfig`, guarded by `settings.storage`, are the only procedures with a section guard, `Resource:Action` remaining the API boundary. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `sectionAccess.set`, `sectionAccess.setRoleDefaults` and `users.approvePending` turn a leaf on — an override `true`, a role default `enabled` — only for a role holding the leaf's mapped permission (`sectionPermissionHeld` in `@luke/core`, the predicate of the resolver's permission fallback), refusing otherwise with `BAD_REQUEST` naming the section, the permission and the role, while turning a leaf off, removing an override, `disabled` and `auto` are never refused for a missing permission and the recovery guard on `settings.users` stays. [ADR-043](../043-section-access-a-leaf-turns-on-only-with-its-permission.md#errata)
- `sectionAccess.set` and `users.approvePending` read the target user's role under a `FOR SHARE` row lock held until commit, the approval checking the role it has just written, and `setRoleDefaults` takes no lock because role permissions are static. [ADR-043](../043-section-access-a-leaf-turns-on-only-with-its-permission.md#errata)
- The permission rule holds at the commit of those writes only: a role change through `users.update` can leave an enabled leaf the new role cannot read without refusal, and stored violations from any source are never changed but listed at every API start, one warning per violation with ids and section keys only, and shown in the access dialogs as on with the missing permission, switchable off. [ADR-043](../043-section-access-a-leaf-turns-on-only-with-its-permission.md#errata)
- In the access dialogs a leaf the role cannot read is shown off and unavailable with its permission in a tooltip, a parent with nothing under it the role may turn on likewise, switching a parent on skips such leaves, and a refused save shows the server's message. [ADR-043](../043-section-access-a-leaf-turns-on-only-with-its-permission.md)
- `UserAccessDialog` and `ApproveUserDialog` render `SectionAccessList`, which resolves every switch with the core `effectiveSectionAccess` and shows none until `sectionAccess.getDefaults` has answered, and a parent switch, a reset and the "overridden" mark act only on the leaves under the section the kill switch does not cover, a kill-switched leaf being shown off and locked with its override and pending edit never written, deleted or reset. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- `useSectionOverridesEditor` holds a fresh read taken at each opening plus the administrator's edits, never changed by a background refetch, sends the edits on editable leaves as absolute values, disables every control (and Escape) until the save and its reconciliation end, replaces its state with a fresh read after any outcome, and refuses further attempts until reopened if that read fails. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- The editor does not guarantee the outcome when two administrators edit the same field at once, where the last write wins, nor for an edit dropped because it equalled the role default, which follows a role default changed while the dialog is open. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
- Approving a pending user is one `users.approvePending` call carrying address, role, overrides and team in one transaction, and after a failure the dialog re-reads the role, the pending status and the overrides, ending without a second approval for an account no longer pending. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md#errata), [ADR-044](../044-pending-user-approval-in-one-transaction.md) (Sessions and accounts)
- Every sub-section folder under `apps/web/src/app/(app)/` has its own `sectionLayout('<leaf>')` layout (`apps/web/src/lib/authz/sectionLayout.ts`, a missing one failing `sectionLayouts.test.ts`), so a page whose section is off is not opened by URL, checked when the server renders the section and not on navigation between its own pages, and a dashboard widget showing a section's data needs that section visible and its permission held (`useWidgetAccess` in `widgetRegistry.ts`). [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md#errata)
- Migration `20261001220553_section_access_leaf_overrides` is hand-written SQL in one `DO` block with the hierarchy, static table and permission fallback frozen in the file, and runs once, through `prisma migrate deploy` or the backup migration bridge, because a second run would delete child grants made since. [ADR-027](../027-section-access-leaf-overrides-and-validated-defaults.md)
