# Decisions in force — Permissions

> Current guidance, kept up to date; not a decision record. The ADRs linked here decide: where this page and an Accepted ADR disagree, the ADR holds.

_Last reviewed: 2026-11-22_

## Rules in force

- Resources, actions and `VALID_RESOURCE_ACTIONS` are declared in `packages/core/src/auth/permissions.ts`, and the static, version-controlled `ROLE_PERMISSIONS` map there is the only list of what `admin` (`*:*`), `editor` and `viewer` hold; AppConfig `rbac.*` keys change section visibility only. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md), [ADR-042](../042-resource-action-permissions-session-only-builder-for-maintenance-reads.md)
- `hasPermission(user, permission)` evaluates `*:*`, then `resource:*`, then the exact permission, and answers `false` for a role outside `Roles`. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- `protectedProcedure` is the one authenticated builder with a permission: every procedure on it declares its permission with `requirePermission` (a single permission, an OR-array, a declaration or an input resolver) and passes the maintenance guard, administrator-only procedures included. [ADR-042](../042-resource-action-permissions-session-only-builder-for-maintenance-reads.md), [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- `sessionProcedure` (`apps/api/src/lib/trpc.ts`) requires a valid session and nothing else — no maintenance guard, no permission, never a write — and serves only a read every signed-in user needs during maintenance, today only `maintenance.mode.getStatus`, each use carrying a reasoned `nosemgrep: luke-procedure-requires-permission` and listed in ADR-042. [ADR-042](../042-resource-action-permissions-session-only-builder-for-maintenance-reads.md)
- `publicProcedure` is only for calls before a session, and nothing answered before sign-in tells the caller the application's state, the maintenance state included. [ADR-042](../042-resource-action-permissions-session-only-builder-for-maintenance-reads.md)
- `selfProcedure` declares own-data procedures: it writes only the caller's rows, takes no target user id, and reads the caller's rows plus what computing the caller's own view needs, with `me.changeEmail` the one declared exception; nothing verifies a handler keeps this contract, it is a declaration for review. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- A check `requirePermission` cannot express is made in the handler with `can()` or `hasPermission()` — the AND of `editLock.acquireMany` and `renew` (with a reasoned `nosemgrep`), the `config:update` needed to read a config value raw or decrypted, and the `*:*` that `users.update` needs for a password, a privileged field or a role — and a reasoned `nosemgrep` also marks a procedure open to every signed-in user by design (`feedback.submit`). [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- A read-only query takes `read`, except a preview of the mutation it precedes, which takes that mutation's permission, and a read serving only an administration create/edit dialog or tab, which takes that dialog's or tab's permission (either one for a picker shared by create and edit); each carries an in-chain `// Rule 5:` marker right after its permission middleware, which `.semgrep/rules/query-mutating-permission.yml` requires on any `protectedProcedure` query gated by a literal non-read permission (`*:*` aside). [ADR-049](../049-resource-action-permissions-previews-dialog-reads-and-the-phase-catalog-on-read.md)
- `.semgrep/rules/procedure-requires-permission.yml` fails any query, mutation or subscription on `protectedProcedure` or `sessionProcedure` whose chain has no `.use(requirePermission…)`, and any router that binds either builder to a name; it proves the middleware is present, not that it asks for the right permission. [ADR-042](../042-resource-action-permissions-session-only-builder-for-maintenance-reads.md), [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- Raw routes (`apps/api/src/routes/`) use `requireSessionWithPermission` with the permission of the procedure that links the file, and presigned uploads take theirs from `PRESIGNED_UPLOAD_PERMISSION`. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- Every refusal of a Resource:Action permission or a section — by `requirePermission`, a manual check, `withSectionAccess` or `requireSessionWithPermission` — writes one `Permission denied` warning through `logAccessDenied` (`apps/api/src/lib/permissions.ts`) with `traceId`, `userId`, `userRole` and the requested and denied permissions or the section, while the client message names no permission and brand-scope, ownership, self-protection and data-rule refusals write no such line. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- An operation reserved to administrators requires `*:*` (`requirePermission('*:*')` on the server, `can('*:*')` in the web) when another role holds the resource through `resource:*` or when it acts on authorization itself: the permanent delete of brands, seasons and vendors (still `*:*` although no role holds those wildcards any more) and the purge of brands and seasons with its preview, the unrestricted brand and function scope (`context.service.ts`), forcing and revoking local access, a password reset, privileged field or role within `users.update`, and section-access management (`sectionAccess.getDefaults`, `getByUser`, `set`, `setRoleDefaults`). [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md) ([errata](../029-resource-action-permissions-one-builder-logged-refusals.md#errata)), [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- Where no other role holds the resource through a wildcard, an action only `admin` holds is enough — `pricing:update`, `config:update`, `maintenance:update`, `maintenance:mode_manage`, `sales:sync`, `collection_layout:configure`, `season_calendar:configure` — and a new action on a resource with a wildcard grant is no substitute for `*:*`. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md), [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- Bypassing maintenance is `maintenance:update` (`bypassesMaintenance`), shared by the tRPC guard, the login flow, the force-logout and the web `MaintenanceGate`, while changing the mode (`maintenance.mode.schedule`, `activateNow`, `cancelScheduled`, `end`) is `maintenance:mode_manage`, which during an active window only a caller who also bypasses maintenance reaches. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- For resources mapped to leaf sections through `SECTION_TO_PERMISSION`, every role holding a mutating permission (any action but `read`, `read_all`, `view_revisions` and `export`) has at least one mapped leaf visible in `SECTION_ACCESS_DEFAULTS` and every default-visible leaf has its mapped permission granted, enforced by `packages/core/src/rbac/__tests__/sectionHierarchy.test.ts` per resource, with `settings`, `company_function` and `company_team` outside it, and runtime section overrides never grant a permission. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- `editor` holds `brands:read`, `seasons:read` and `vendors:read` instead of the wildcards and no `users:update`, and `viewer` holds no `sales:read`, so it reads no sales figure — statistics, their sync state or the home's weekly orders — even with the statistics section switched on by an override. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md#errata)
- `users.update`, `users.approvePending`, `users.forceVerifyEmail`, `users.revokeUserSessions` and `auth.requestEmailVerificationAdmin` require `users:update`, which only `admin` holds through `*:*`, while the `*:*` guards inside `users.update`, the `USER_EDITOR_UPDATABLE_FIELDS` allowlist and the approval that keeps role and section overrides for a caller without `*:*` stay as the default for any future role granted `users:update` alone. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- The manual order-portfolio and KIMO syncs (`sales.statistics.portafoglio.triggerSync`, `sales.statistics.kimo.triggerSync`) require `sales:sync` and the web gates their buttons on it, while both `getSyncState` reads and the `sales.statistics.*.download` exports stay `sales:read`. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- The collection catalog writes (`collectionCatalog.create`, `update`, `remove`, `restore`, `reorder`) require `collection_layout:configure`, to which `admin.collection_layout_configuration` maps, and the vendor closure writes (`holidays.upsertVendorClosure`, `deleteVendorClosure`, `confirmVendorClosures`, `prefillVendorClosures`) require `season_calendar:configure`, while `collectionCatalog.listAll` requires `collection_layout:read`. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- `phase.list({ includeInactive: true })` returns every phase, retired ones included, on `phase_catalog:read`: retired phases label the history and the pickers derive from the same list, and the phase-catalog page reads it (no write-gated full list). [ADR-049](../049-resource-action-permissions-previews-dialog-reads-and-the-phase-catalog-on-read.md)
- A procedure a default-visible page reads requires a permission that page's roles hold, never `config:*`: `holidays.listHolidays` requires `season_calendar:read`, both `getSyncState` return the replica's schedule for the statistics page, and `integrations.nav.sync.getFilter`, which returns the whole NAV sync filter, stays `config:read`; importing and deleting holidays stay `config:update`. [ADR-038](../038-resource-action-permissions-grants-follow-section-visibility.md)
- Authorization reads a permission, never a role name: `usePermission` exposes `can`, `isAuthenticated` and the `session` and no role helper, and comparisons of another user's role (protecting the last administrator, refusing a section override on an administrator, expanding a calendar audience) are data rules this model does not govern. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md#errata)
- In the web, creation controls use `CreateActionButton` and table actions `PermissionButton`, or `PermissionTooltip` when the control is not a `Button`, and the server check stays authoritative. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
- Section visibility and brand scope are layers stacked after the permission check, never replacing it, and a section write turns a leaf on only for a role holding its mapped permission. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md), [ADR-043](../043-section-access-a-leaf-turns-on-only-with-its-permission.md) (Section access)
- A procedure acting on one calendar event by id goes through `resolveEventBrandAccess`, which checks the brand and then the event's visibility, so `season_calendar:update` no longer guarantees a write inside an allowed brand: an event the caller cannot list answers `NOT_FOUND`, for reads and writes alike, while a brand outside the caller's scope stays `FORBIDDEN`; `locate` answers `NOT_FOUND` for both. [ADR-040](../040-calendar-events-access-by-id-and-masking-outside-the-calendar.md) (Calendar)
- Adding a resource or action updates `RESOURCES`/`ACTIONS`, `VALID_RESOURCE_ACTIONS` and `ROLE_PERMISSIONS` together, a `resource:*` grant covers actions added later, and permissions follow the role the session carries, reaching existing sessions through session revocation. [ADR-029](../029-resource-action-permissions-one-builder-logged-refusals.md)
