# Decisions in force — Sessions and accounts

> Current guidance, kept up to date; not a decision record. The ADRs linked here decide: where this page and an Accepted ADR disagree, the ADR holds.

_Last reviewed: 2026-11-22_

## Rules in force

- A session is revoked on the server by changing what the API compares every token against, the user's `tokenVersion` and `isActive`, and independently of any revocation it ends 12 hours after its login. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `createToken` (`apps/api/src/lib/auth.ts`) signs the API token with the user's `tokenVersion` and the session's required `authTime` — the login's time from `authenticateUser` (LOCAL and LDAP login), the bearer's own from `auth.refreshToken` — and sets `exp` 8 hours after signing or at `authTime` plus the absolute lifetime, whichever comes first. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- The absolute lifetime is the constant `SESSION_ABSOLUTE_LIFETIME_SECONDS` (`packages/core/src/schemas/auth.ts`), 12 hours, and is not configuration. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `createUserSession` refuses a bearer whose `authTime` is missing, not a finite number, ahead of the clock by more than the 5-second JWT tolerance, or at or past `authTime` plus the absolute lifetime, whatever its `exp` says. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `verifyTokenVersion` (`apps/api/src/lib/tokenVersionCache.ts`) accepts a token only when its `tokenVersion` equals the user's current value and the user is active, rejecting a token without the claim and a user that no longer exists, and `authenticateRequest` applies both checks to tRPC procedures and raw routes, while `authMiddleware` repeats the version check for contexts built by hand, which carry no bearer and to which the lifetime does not apply. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `auth.refreshToken` re-reads the user and re-mints the token with the role and version it reads, refusing with `UNAUTHORIZED` a session without `authTime`, an inactive or missing user and a version that is no longer the bearer's, and keeps the bearer's `authTime`, so refreshing never extends a session. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `auth.logout` increments the caller's `tokenVersion`, invalidates the cache and writes an `AUTH_LOGOUT` audit row, ending every session of the user, and as a `selfProcedure` it is refused during an active maintenance window to a user who cannot bypass it; the browser session is cleared all the same. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md), [ADR-048](../048-session-revocation-signing-out-always-ends-the-browser-session.md)
- Every sign-out control — the sidebar, the context gate, `app/error.tsx`, `app/global-error.tsx`, `app/not-found.tsx`, the maintenance lock screen and the `/logout` confirmation page, which the lock never covers — is a native form post (`LogoutForm`) to `POST /api/auth/logout` (`serverLogout`), which works without JavaScript; a GET there answers 405. [ADR-048](../048-session-revocation-signing-out-always-ends-the-browser-session.md)
- `serverLogout` first checks provenance — `Sec-Fetch-Site: same-origin`, or else an `Origin` (failing that a `Referer`) equal to the public origin (`NEXTAUTH_URL`'s, the request's own when unset), `Origin: null` refused — and a refused request changes nothing and goes to `/logout`. [ADR-048](../048-session-revocation-signing-out-always-ends-the-browser-session.md)
- It reads the session cookie under the app's cookie name, salt and secret, never through `auth()`, calls `auth.logout` with its bearer within 5 seconds, always clears every session cookie chunk with `signOut({ redirect: false })`, and answers a 303 to `/login`, or to `/login?signout=incomplete` — which tells the user the other devices' sessions stay open until they expire — when the call did not succeed or answer `UNAUTHORIZED` and a session cookie was there to end. [ADR-048](../048-session-revocation-signing-out-always-ends-the-browser-session.md)
- The automatic sign-outs (`useSessionVerification`, `HeartbeatTicker`, the force-logout route, the password change, `me.revokeAllSessions`) do not call `auth.logout`: their sessions are already revoked or expired. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `verifyTokenVersion` caches each user's `tokenVersion` and `isActive` in a process-local map for `security.tokenVersionCacheTTL` (10 to 600 seconds, 60 by default, the setting re-read every five minutes), and every runtime write that revokes sessions must invalidate it, with `invalidateTokenVersionCache` for one user or `clearTokenVersionCache` after a bulk change. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- Each invalidation advances a process-local counter and a cache fill stores its read only if the counter has not moved since the read began, a verification already reading still answering from its own read, and invalidation holds only on the single API instance ADR-011 requires. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `notifications.getSseTicket` issues a single-use ticket valid for 60 seconds carrying `userId`, `tokenVersion` and `authTime`, refusing a session without the last two, and the SSE route (`apps/api/src/routes/sse.ts`) checks it with `isSseSessionLive` when the stream opens (401 before any stream exists) and then every 30 seconds without overlap, ending the stream on a refused or failed check and, by its own timer, at `authTime` plus the absolute lifetime. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- Ending an event stream clears both its timers and removes it from the push pool before it ends, and a check resuming after the stream closed writes nothing. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- The NextAuth `jwt` callback (`apps/web/src/auth.ts`) delegates the check to `auth.refreshToken`, ends the session on `UNAUTHORIZED` and runs at most one refresh per user every 30 seconds, `useSessionVerification` calls `me.get` on mount, every 10 seconds and on focus or visibility change, `HeartbeatTicker` calls `users.heartbeat` every 60 seconds, both signing out on `UNAUTHORIZED`, and there is no Next.js middleware or proxy check. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `tokenVersion` is incremented, and the cache invalidated, by `auth.logout` and `me.revokeAllSessions` for the caller, `users.revokeUserSessions` for another user (any user, administrators included, but never the caller), `me.changePassword` and `auth.confirmPasswordReset`, `users.update` when the role, active state, password or an administrator-only field changes, and `users.revokeLocalAccess`. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `users.softDelete` sets `isActive` to `false` and invalidates the cache without incrementing, and `users.hardDelete` deletes the row and invalidates that user's cache entry. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- `forceLogoutNonAdmins` (`apps/api/src/lib/maintenanceMode.ts`) increments every non-admin user's `tokenVersion` and clears the cache, called by the maintenance scheduler and `maintenance.mode.activateNow` when the window is set to `forceLogout`, always at the start of `maintenance.backup.restore`, and again in its `finally` block after `pg_restore`; the restore can still undo admin session revocations and account deactivations made after the backup, because `pg_restore` brings back `tokenVersion` and `isActive` and the final increment re-revokes only non-admin sessions. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- Outside the runtime triggers, migration `20260515000000_company_structure` increments every user's `tokenVersion` once without obliging future migrations to do so, and `seedAdminUser` (`apps/api/prisma/seed.ts`) can reactivate an existing admin without incrementing, as a bootstrap path rather than a revocation path. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- A new token issuance path must decide where its session starts, since `createToken` requires `authTime`, and a new revoking path must pair its database write with the cache invalidation, which nothing couples. [ADR-039](../039-session-revocation-tokenversion-and-absolute-lifetime.md)
- No single runtime call revokes every user's tokens, and replacing the master key is not a supported way to revoke sessions: revoking many at once is done by incrementing token versions. [ADR-020](../020-master-key-scope-and-rotation-limits.md#errata) (Secrets and sensitive data)
- `users.approvePending` takes the team and, from an administrator (`*:*`), the address, the role and the section overrides, and applies them in one `$transaction` in the order address, role, overrides, team and approval, so a refusal anywhere leaves the account as it was and the dialog makes one call per attempt. [ADR-044](../044-pending-user-approval-in-one-transaction.md)
- In the approval the address goes through `moveUserEmail` (stored form, unique constraint, unverified, links revoked, an `EMAIL_CHANGED` row), a new address or role ends the account's sessions as in `users.update`, each override goes through `applySectionOverride` with the leaf-permission check against the role just written, and the lock order is the last-admin lock, then the user row. [ADR-044](../044-pending-user-approval-in-one-transaction.md)
- For an account on a synthetic address the dialog asks an administrator for a real one and shows anyone else why they cannot approve, the approval replaces only a synthetic address and refuses to replace one the user gave meanwhile, the server refuses an approval that would leave the address synthetic, and after the commit the new address gets its verification link. [ADR-044](../044-pending-user-approval-in-one-transaction.md)
- After a refused approval nothing of the attempt is stored, and the dialog re-reads the stored role, the pending status and the overrides and keeps the administrator's choices for another attempt. [ADR-044](../044-pending-user-approval-in-one-transaction.md)
