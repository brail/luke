# Decisions in force — Storage

> Current guidance, kept up to date; not a decision record. The ADRs linked here decide: where this page and an Accepted ADR disagree, the ADR holds.

_Last reviewed: 2026-11-22_

## Rules in force

- An entity refers to a stored file by its key in a known bucket (`Brand.logoKey`, `CompanyProfile.logoKey`, `CollectionLayoutRow.pictureKey`, `CollectionLayoutRowRevision.pictureKey`, `MerchandisingImage.key`), and no model stores a stored file's URL. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- Uploads, their derivatives and copies into the immutable bucket each get a `FileObject` row, unique by `bucket` and `key`. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- URLs are derived when a response is built: `makeUrlResolver(prisma)` reads the storage configuration once and resolves any number of keys, and `resolvePublicUrl` wraps it for one key. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- An upload that precedes its entity creates a pending `FileObject` (`confirmedAt: null`): the brand-logo `temp` route, both collection-row-picture routes, the company-logo route, the specsheet-image route, and `storage.confirmUpload` after a presigned upload. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- A client links a pending file by its `fileObjectId`: the brand and company inputs accept no logo key but `null`, which removes the logo, and a collection row's key comes only from a confirmed pending upload, `removePicture` clearing it. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md#errata)
- `confirmPendingFile` links the file inside the `$transaction` that writes the entity — `brand.create`, `brand.update`, `collectionLayout.rows.create`, `collectionLayout.rows.update`, `company.profile.update`, and the specsheet-image upload's own locked transaction — returning the key only for a still-pending file of the same user in the expected bucket, and confirming its derivatives in the same call. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- A pending id that no longer resolves is refused with `BAD_REQUEST` and changes nothing, in brand, company and collection-row saves alike. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md#errata)
- `/upload/brand-logo/:brandId` is the one upload that is not two-phase: it stores the file as confirmed and writes the brand outside any transaction, so a failed brand write leaves an orphan the cleanup never removes (an open gap); a route that stores a file as confirmed must check that its entity exists before it uploads. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- A client may presign only into a bucket of `PRESIGNED_UPLOAD_BUCKETS` (today `company-assets` alone), each carrying the permission of the procedure that links its files, which `storage.requestUpload` requires; making another bucket presignable is a decision about that permission. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- The bucket and key of a presigned upload come from the token `storage.requestUpload` signs, never from client input, the slot's user must be the caller, and `storage.confirmUpload` re-checks the slot's bucket against the list. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- `setupTempFileCleanup` runs at start and every 30 minutes, without a scheduler lock, and removes pending master files older than one hour in every `IMAGE_BUCKETS` bucket, their derivative objects first, keeping a master whose derivative could not be deleted for the next run; a confirmed file is never swept. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- With the S3 provider a file URL is always `/api/uploads/{bucket}/{key}`, served by a web route that requires a session and fetches from the API route `/uploads/:bucket/*`; local storage returns the same proxy URL while `storage.local.enableProxy` is on, its default. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- The API route `/uploads/:bucket/*` checks no session and serves only application buckets: it relies on apps/api being unreachable from outside the deployment. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- With `storage.local.enableProxy` off the resolver returns direct `{publicBaseUrl}/uploads/{bucket}/{key}` URLs, which work only where browsers reach the API, and with `storage.local.publicBaseUrl` also unset resolving any URL throws. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- `APP_STORAGE_BUCKETS` is the only list of application buckets, from which the serving route, provider initialization, and backup and restore derive; `isValidBucket` adds only `backups`, which the serving route refuses and no client can presign into. [ADR-031](../031-key-based-storage-two-phase-upload-and-presigned-buckets.md)
- The S3 provider is named for the protocol, not a vendor: `S3Provider` (`apps/api/src/storage/providers/s3.ts`) on `@aws-sdk/client-s3` alone, the `storage.s3.*` keys, `storageTypeSchema` `'local' | 's3'` and `storage.testS3Connection`. [ADR-012](../012-generic-s3-storage-provider.md)
- The compose stack's S3 backend is SeaweedFS, pinned as `chrislusf/seaweedfs:4.48` in `docker-compose.dev.yml`, `docker-compose.prod.yml` and `docker-compose.rc.yml` with the gateway's admin identity passed as `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, and without an init sidecar: `S3Provider.init()` creates the buckets idempotently. [ADR-012](../012-generic-s3-storage-provider.md#errata)
- `apps/api/scripts/migrate-storage.ts` is the one migration script between providers: `--from`/`--to` (`local`, `s3`), `--from-s3-*`/`--to-s3-*` overrides, and `--fix-mime`, which corrects both the `FileObject` row and the destination object's metadata. [ADR-012](../012-generic-s3-storage-provider.md)
- `packages/core/src/storage/assets.ts`, free of `sharp`, declares `ASSET_PIPELINE_VERSION`, the `ASSET_VARIANTS` presets (`thumb`, `card`, `export`), one `ASSET_KINDS` entry per upload path and `buildVariantKey()`; a new upload path is one registry entry. [ADR-013](../013-asset-derivative-pipeline.md)
- `normalizeMaster()` (`apps/api/src/lib/assets/pipeline.ts`) bakes EXIF orientation, converts to sRGB and takes the content type from the decoded bytes, never the extension; `deriveVariant()` never upscales and keeps alpha as PNG; both are guarded against decompression bombs. [ADR-013](../013-asset-derivative-pipeline.md)
- Every upload path calls `ingestImageAsset()` (`apps/api/src/services/asset.service.ts`), which generates the kind's sync variant inline, defers the others to the worker and marks a master that fails to decode `FAILED`; a variant not yet produced falls back to the master's bytes, except for the `export` variant over a WebP master. [ADR-013](../013-asset-derivative-pipeline.md)
- `FileObject` is a tree whose `parentId = null` rows are masters; its self-relation cascades on delete by design, and the derivatives' physical objects are removed by `deleteObjectByKey` and the orphan-file reaper. [ADR-013](../013-asset-derivative-pipeline.md#errata)
- `enqueueDerivatives()` (`apps/api/src/lib/assets/derivativeWorker.ts`) is capped with `p-limit`, and `registerDerivativeScheduler` runs a 5-minute reconcile under `withSchedulerLock` that picks up missed masters, retries up to 5 attempts, catches a stale `pipelineVersion` and runs the backfill (`scripts/backfill-asset-derivatives.ts`). [ADR-013](../013-asset-derivative-pipeline.md)
- The kill switch `storage.derivatives.enabled` is read fresh, never cached, by sync ingest, the worker and the reconcile tick. [ADR-013](../013-asset-derivative-pipeline.md)
- `readAssetBuffer()` resolves a variant from the row's stored content type and dimensions, never the key's extension, and returns `null` rather than a WebP master when the `export` variant is not ready. [ADR-013](../013-asset-derivative-pipeline.md)
