# Collection Genome — Adoption in LUKE

**Ref.** "Genoma della Collezione: Algoritmo di Alert e Sistema di Monitoraggio
Avanzamento" (Collection Genome: Alert Algorithm and Progress Monitoring System;
Rev. 1, A. Zordan, 1 July 2026)
**Status**: feasibility analysis and mapping onto the existing architecture. The
implementation plan (tasks, migrations, estimates) is a separate document,
downstream of this one.

## Background

The original document describes a new conceptual system (PHASE, CALENDAR
TEMPLATE, CALENDAR INSTANCE, COLLECTION LAYOUT, Alert Engine). In LUKE most of
these entities already exist, under other names, as a result of the calendar
work carried out over the past months. This document reconciles the two
vocabularies and points out where the data model needs extending, where reuse is
enough, and where we chose a different approach from the one assumed in the PDF
— with the reasoning.

## 1. The Static Core

| PDF concept | LUKE counterpart | Notes |
|---|---|---|
| PHASE | New `Phase` entity (ordered catalog) | When this analysis was written there were two separate, unconnected catalogs: the production state of the collection row (`CollectionLayoutRow.progress`) and the calendar event type (`CalendarEvent.type`). We unify them into a single `Phase` catalog, shared by both domains. This is the foundation that makes it possible to compare "which phase the row is at" with "which phase the calendar is at" in the same language. |
| CALENDAR TEMPLATE | `MilestoneTemplate` + `MilestoneTemplateItem` (already existing) | Each template item will have an optional reference to the corresponding `Phase` (optional because a template can also contain events that do not represent a production phase, e.g. a review meeting). |
| LEAD TIME between phases | Implicit in the template offset | The current mechanism computes the date of each template item as "anchor date + a number of offset days" (`offsetDays`). This produces exactly the same result as the backward calculation described in the PDF, with no need for a new algorithm: if the anchor coincides with the last phase, the negative offsets of the earlier phases *are* the backward scheduling. We do not introduce a new formula; we reuse the existing one with this reading. |

## 2. Seasonal Instantiation

### Aspect A — Timeline

Corresponds to `SeasonCalendar` (existing): one calendar per Brand+Season
combination, containing the events (`CalendarEvent`) generated by applying the
template.

**Clarification with respect to the PDF**: segmentation by Brand+Product
Category, described in the document as the driver for instantiating *multiple*
calendars, does not generate multiple calendars in LUKE. A calendar stays unique
per Brand+Season (that is the very definition of "calendar": the set of all the
events of that context). Segmentation by product category/subset happens instead
**within the calendar, through planning groups** (`PlanningGroup`), described in
section 4.

**Tuning and Freeze**: we introduce a guided step (wizard), opened automatically
after a template is applied to a planning group, in which the user walks through
the events generated from the template one by one and:
- checks/adjusts the date, taking into account the holidays and vendor closures
  already recorded in LUKE.

Which rows an event applies to is not decided in the wizard: it follows from the
event's planning group (see section 4).

At the end of the wizard the planning group can be frozen; freezing can also be
started directly for a planning group, without stepping through its events.
Freezing saves an immutable copy of the dates reached (the official date),
distinct from the "working" date, which stays editable on the event (except for a
phase event whose deadline has already passed, which moves only through a
reschedule with a recorded reason). A later change to the parent template never
alters existing calendars retroactively, frozen or not: applying a template
copies its items into independent events.

### Aspect B — Physical Object

Corresponds to `CollectionLayout` / `CollectionLayoutRow` (existing), with no
structural change to the container. The row→calendar link is already implicit:
the row belongs to a layout, the layout to a Brand+Season, which uniquely
identifies the calendar.

The "Progress Status" described in the PDF corresponds to the row's phase: the
former `progress` field, since migrated to `phaseId`, a reference to the new
`Phase` catalog (see section 1).

## 3. The Recording and Measurement System

We adopt the proposed concept (row/phase/actual-date tuple) with a dedicated
history table, distinct from the general audit log already present in LUKE.
Reasoning: the existing audit log is designed for traceability/compliance (who
did what), not for high-volume statistical queries; a table dedicated to "when
row X reached phase Y" allows direct queries for the variance KPIs described in
the document, without having to interpret free-form content.

## 4. Handling Subsets ("Forks") — via PlanningGroup

This is the point of greatest deviation — and greatest simplification — from the
PDF's initial approach.

The PDF does not explicitly address the case where the same calendar event must
have different dates for different subsets of products (e.g. "Rendering" in July
for one part of the collection, in September for another, with "Final Delivery"
common to all). The solution identified does not require a new rules engine:
**it is obtained by composing data that already exists in the LUKE model**,
through the `PlanningGroup` entity.

> Historical note: a first implementation (commit `1a65b93`, reworked in
> `fe92c6e`) provided *per-event* anchoring — each event could be restricted to a
> subset of rows chosen step by step inside the wizard, with automatic fork/rejoin
> at the level of the single milestone. This mechanism was **removed** (commit
> `a473884`) and replaced by the `PlanningGroup` model described below: simpler to
> reason about, but coarser (the scope is the whole group of rows, not the single
> event — see the limitation at the end of this section).

Mechanism:
- Every Collection Layout row belongs to a `PlanningGroup` (default: a single
  group created automatically per calendar). Assignment happens at row level —
  single (row drawer) or bulk (`bulkAssignPlanningGroup`) — not inside the
  planning wizard.
- Every calendar event also belongs to a `PlanningGroup` — this is how the rows
  it applies to are determined: an event applies to all and only the rows of its
  own group.
- A phase can appear more than once in the same calendar with different dates
  (e.g. two "Rendering" events, one in July in one group, one in September in
  another) simply because they belong to different `PlanningGroup`s — no
  additional anchoring/exclusion logic is needed.
- There is no automatic rejoin: if an event later has to apply to all rows again,
  it must be created in a `PlanningGroup` that contains all of them (typically
  the default group), or the rows must be reassigned to a common group.

For each row, the alert engine considers only the events whose `planningGroupId`
matches the row's (`filterApplicableEvents` in `phaseAlert.service.ts`) —
behaviour equivalent to the one described in the PDF, but implemented by
composing foreign keys rather than by graph logic.

**Known limitation**: the scope is the whole group, not the single event — if
two rows of the same group must diverge on a single event (e.g. "Rendering") but
stay together on all the others, they still have to be moved into two different
groups, which also separates them for the other events unless those are
duplicated in both groups. Re-scoping rows mid-planning requires leaving the
wizard, reassigning the group from the Collection Layout, and coming back — more
laborious than the old per-event anchoring. If this limitation turns out to be a
recurring problem in real use, it should be reconsidered (without, however,
reintroducing the old per-event mechanism as-is, whose configuration and
comprehension cost was judged too high).

## 5. The Alert Engine

We confirm the PDF's approach (Step I: identifying the active event; Step II:
criticality matrix), with two adaptations:

1. **The "Deadline" calculation** is simplified: it coincides with the target
   date already computed for the phase the row is currently in, within the same
   calendar. Mathematically it is equivalent to the subtraction of the
   intermediate lead times proposed in the PDF, but it does not require repeating
   that calculation: the data is already available.
2. **The criticality thresholds (10 days, 5–9 days, etc.) and their associated
   colours are not fixed in code**, but managed in a setting that whoever
   administers the system can configure (the AppConfig key
   `collectionControl.alertThresholds`; the same philosophy already used in LUKE
   for other process parameters). This makes it possible to tune the thresholds
   over time without technical intervention, and in future also to change the
   number of criticality levels, if needed.

The alert calculation is not stored in the database: it is recomputed whenever
it is needed, against the current date. The choice is driven by the wish to
avoid duplicated state that can drift out of line with the source data.

## 6. High-Level Monitoring System

We confirm the three proposals of the original document, to be built as views
within LUKE's Product area, visible to users granted the `product.control`
section (permission `collection_alert:read`):

1. **Saturation Heat-Map Dashboard** — view by Brand × Category, as proposed.
2. **Bottleneck Index** — view by active event, as proposed.
3. **Predictive Stagnation Monitoring** — based on the historical data in the
   table described in section 3, as proposed.

No substantial change from what the PDF describes on this point.

## Summary of Deviations from the Original Document

| PDF point | LUKE choice | Reason |
|---|---|---|
| Multiple calendars per segment | Single calendar per Brand+Season, segmented by planning group (`PlanningGroup`) | Consistency with the definition of "calendar" already in use; avoids a proliferation of instances to manage separately |
| Explicit calculation of the Deadline by summing lead times | Direct reuse of the target date already computed for the current phase | Same result, no duplicated calculation |
| Alert thresholds implicit in the text | Thresholds and colours in a configurable setting | Avoids hardcoding, allows tuning without a release |
| No explicit treatment of subsets/forks | Events and rows scoped by `PlanningGroup`, without a graph engine | Covers the real case (see the shared diagram) without reintroducing the complexity of the constraint engine that had just been removed |
